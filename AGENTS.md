# thinwire — agent notes

## Product lock (S2)

- v1 protocols: Telegram, WhatsApp (experimental), Discord (bot/OAuth inbox only), Slack OAuth, Signal (experimental; AGPL helper process, #248, ADR `0013`)
- Accepted plan, ADR `0013-ship-all-protocols-agpl-helpers` (2026-10-08): release builds ship every protocol, with WhatsApp and Signal in AGPL-3.0-only helper binaries over IPC. It supersedes `0004` (Signal out of v1) and `0011` (AGPL protocols local-only). Both helpers are in the tree: the WhatsApp helper (#246) and the Signal helper (#248)
- The MIT app binary never links AGPL code. Feature `whatsapp-web` has two parts. In `thinwire-whatsapp` it links the AGPL `wacore-libsignal` into the helper program `thinwire-whatsapp-helper`. In `thinwire` and `thinwire-core` it adds the WhatsApp screens and the MIT helper adapter, with no AGPL code. Feature `signal-local` has the same two parts: in `thinwire-signal` it links Presage and libsignal into the helper program `thinwire-signal-helper`, and in `thinwire` and `thinwire-core` it adds the Signal screens and the MIT helper adapter. Release builds and OS zips turn on both parts of both features. No MIT crate depends on `thinwire-whatsapp` or `thinwire-signal`, also not as an optional dependency. `scripts/check-agpl-deps.sh` and `scripts/check-release-tree.sh` enforce this
- Public CI can download AGPL source. Cargo fetches every git dependency in `Cargo.lock`, including optional ones. The default public CI jobs stay feature-off. One separate job, `release-features`, builds and tests every feature that a release ships (`telegram-tdlib`, `slack-oauth`, `discord-bot`, `whatsapp-web`, `signal-local`, and the WhatsApp and Signal helpers with their clients; `0013`). A change to a workflow file needs an owner push, because the bot token has no workflow scope. The helper crates are the only place AGPL code may link
- Code that links an AGPL library moves into an AGPL-licensed crate folder in this repo (#77). The root license stays MIT
- README must keep the three risk bullets
- Never claim WhatsApp or Discord personal clients are “reliable”
- Discord: no self-bots / user-account automation
- UI: egui + eframe; protocol work off the UI thread
- WhatsApp, Discord, and Slack work runs in parallel with Telegram (lock change 2026-09-23). It does not wait for "Telegram feels usable"
- Default build: First-run / Add account offer Telegram only. WA / Discord / Slack auth UI exists only when its cargo feature is on. Default and public CI jobs stay feature-off, except the `release-features` job of `0013`
- A test must hold in every feature build, because `release-features` turns on every release feature. A test of one protocol hides the other account rows with `test_support::show_only`. A test of the first-run screen ends the start-up resume first
- Theme default is System (follow OS light/dark live via egui `system_theme`; persist System \| Light \| Dark)
- README image points at `several_protocols-{light,dark}-1100x720.png` in `crates/thinwire/tests/snapshots/`; if that test is renamed or removed, update the README link
- In-app video (ADR `0015`, feature `video`): GStreamer `playbin` with an `appsink`, linked at run time. Only LGPL parts and the decoders of the platform ship. `video` is in `all-protocols` and in `release-features`. The macOS zip has it: `scripts/install-gstreamer-macos.sh` installs the runtime of the official GStreamer framework (version and SHA-256 pinned) and writes small pkg-config files for the build, and `scripts/bundle-gstreamer-macos.sh` copies a small LGPL runtime into `Thinwire.app`: the libraries into `Contents/Frameworks` and the plugins into `Contents/PlugIns`, with no subfolder, because codesign reads a folder there as a nested bundle. The app scans `Contents/PlugIns` at start. The notices are in `third_party/gstreamer/`. The Linux and Windows zips do not have `video` yet: the Linux zip must start on a system with no GStreamer. Telegram clips (video, animation, video note) play now. The helpers and Discord send no video yet
- More than one account for each protocol (ADR `0014`, 2026-11-05). `ProtocolId` is a kind and a slot from 0 to 8. Account 0 keeps every old keychain name, folder, and settings key. Account `n` adds `#n` to keychain names and file keys, and `-n` to folders (`tdlib-n`, `whatsapp-n`, `signal-n`). The Telegram `api_id` and `api_hash` are shared. Each WhatsApp or Signal account has its own helper process, started with `--account n`. Adapters see account 0 only: the host routes each command and tags each event with its account (`ToAccount`, `FromAccount`). One login screen is open for each protocol at a time. A login event of another account does not change it. Remove forgets the account in the settings and deletes no data
- Message menu (2026-11-06): a right click on a bubble offers Reply, an emoji reaction, Copy text, Edit, Forward…, Select, and Delete. Delete asks first. "Also delete for everyone" shows only for an own message. `ProtocolCapabilities::message_actions` says what each protocol offers, and the menu shows only that. The reactions of a message show under its bubble, and a reply shows the message it answers. A click on that quote scrolls the thread to the message it answers, and the bubble of that message glows for 1.5 s. When that message is not loaded, the core loads older pages, at most 5 for each click (`REPLY_JUMP_PAGES`). A change of chat stops the jump. Telegram has every action. Forward (#512, `MessageActions::forward`) shows for a message that the server has (`state::can_forward`). Forward… opens a chat picker of the same account, with search. Select starts the selection mode: a click on a bubble adds or removes it, and the bar over the compose field shows the count, Forward…, and Cancel. Esc closes the picker, then ends the selection. The core sends one `AdapterCommand::ForwardMessages` with every id. Telegram forwards text and media with `forwardMessages`, 100 messages for each request, in id order. WhatsApp and Signal do not forward yet (#533, #534). Edit (#509, `MessageActions::edit`) shows for an own text message that the server has (`state::can_edit`). It puts the text in the compose field, and the draft of the thread waits. Enter saves, and Esc, a chat switch, or a delete of the message cancels. Then the draft comes back. The edit text never becomes a draft. Only Telegram edits now (#518): the adapter asks `getMessageProperties` first and refuses a message that `can_be_edited` does not allow. An edited message shows "edited" before its time (`ChatMessage::edited`, from `edit_date`, `MessageEdited`, or `MessageBody`). The Discord bot replies, reacts, and deletes its own messages: Discord has no delete for one account. The invite asks for Add Reactions, so an older install must invite the bot again for reactions. WhatsApp has every action through wire version 6: the helper counts the reactions of each cached message (one for each person) and keeps them, and the replies, in `inbox.sqlite`. Signal replies, reacts, and deletes an own message for everyone: Signal has no delete for one account. The Signal helper counts reactions in memory for this run (`react::ReactionBook` in the session): the live ones, and the stored ones of each history page in time order. A reaction to a message on an older page shows when that page loads. Slack offers no action yet (#477)
- Collapsed sidebar (2026-11-06): the chevron next to the brand name collapses the account sidebar to one column of protocol tiles (`Intent::SetRailCollapsed`, `rail_collapsed` in `settings.toml`, default off). Each tile keeps its state dot and its unread count, and its tooltip has the name and the state line. A problem state colors the dot. Add account and Settings stay as icons. The lines under an account row (Restart, Link, Retry) and Add Slack workspace need the full sidebar. The other chevron expands it again, at its old width
- Accessibility (2026-11-07): a screen reader and an automation tool find a widget by its AccessKit name. Every text field has a name (`a11y::name`, or the `name` argument of `ui::edited`). A placeholder is not a name. A chat row is one click target: its labels are not selectable. The name of a bubble has its status in words, after the text: "edited", and for an own message "sending", "sent", "read", or "not sent". On Linux, AT-SPI reads the name of a `Label` node from its value, so a label with a painted glyph sets both (`a11y::name_label`). Tests check names as AT-SPI reads them (`atspi_name` in `inbox_keys.rs`). Two gaps are in `accesskit_unix` 0.24, not in this repo: the role name is empty, and AT-SPI `InsertText` is not supported (only `SetTextContents`, which is AccessKit `SetValue`)
- Typing indicators (#510, 2026-11-08): `ProtocolCapabilities::typing` says that the adapter answers `AdapterCommand::SetTyping` and sends `AdapterEvent::Typing`. The core keeps the state in `typing.rs`. A change of the draft of the open thread sends "typing" at most one time each 5 s, and a draft that becomes empty sends a stop. A send sends no stop, because the message ends the typing state on the other side. No state goes out for an edit, a read-only chat, or a closed topic. A person shows as typing over the compose field for 6 s after the last event ("Ada is typing…"). A live message of that person ends it at once: the core finds the person by the sender name of the message. The line is a polite live region for a screen reader. Settings > Chats > "Show others when I type" (`send_typing` in `settings.toml`, default on) stops the outgoing state, and a turn-off sends a stop at once. Only Telegram has typing now (#523): `sendChatAction` with Typing or Cancel, sent off the worker loop, and `updateChatAction`, where only "typing a message" counts. WhatsApp, Signal, and Discord do not have it yet (#524, #525, #526)
- Ordered next work: see `ROADMAP.md`

## Stack

- Rust 2024 workspace, egui/eframe, tokio for async adapters
- Telegram: TDLib / tdlib-rs preferred
- WhatsApp: unofficial linked-device path on `whatsapp-rust` (oxidezap) — ToS risk. Experimental client is feature `whatsapp-web` (`whatsapp-rust`, git rev pinned). Not the default UI. Default CI stays feature-off. Full-screen ToS/ban gate before any QR or pair UI. Session file stays in app-data. The helper encrypts `device.sqlite` with SQLCipher. WhatsApp sends a history sync at a new pairing, and the helper keeps the chat list and the newest messages of each chat in `inbox.sqlite` beside it, encrypted with the same key. An older page the user fetched is written there too. The next start has no mark for it, so the next insert trims that chat back to the newest messages. The oldest cached message asks the phone for an older page. "Start of chat" is only when that page has no older message. It writes the changed chats every 5 s and at shutdown. A revoked device deletes both files, and a new pairing starts an empty cache. The key is random and stays in the OS keychain (`whatsapp.store_key`). The key does not cross the pipe. This encryption does not stop a program that runs as the same user and can read the keychain. A keychain that cannot save the key does not link, and it does not write a store. A keychain read that fails on a saved account keeps the row linked, shows "Can't read the session key from Keychain. Allow access, then retry." and Retry, and does not move the store. Retry reads the key again. A first link shows "WhatsApp did not link." A missing or wrong key keeps the store files: the helper moves them into a folder beside the session folder, leaves `helper.lock` in place, and the row leaves the linked state. It shows "Can't open the saved WhatsApp session. Your old data is kept. Link again" and Link. Link opens the ban gate and does not delete the old files. If the helper cannot move those files, they stay in the session folder. Nothing is deleted. The row stays linked. It shows "The saved WhatsApp session could not be moved aside. It was left in place. Nothing was deleted." and Retry. Retry tries the move again. It does not start a new link and it does not delete anything. Never call it reliable. The client is `crates/thinwire-whatsapp` (AGPL-3.0-only, #77). It links AGPL `wacore-libsignal`, so it runs in the helper program `thinwire-whatsapp-helper` (`0013`, #246), not in the app. `thinwire-protocol` keeps an MIT stub, the MIT helper adapter, and `WhatsAppPhoneVault`. It does not depend on the AGPL crate.
- Helper process rules (`0013`, `0012` section 2 and 4):
    - The app talks to a helper only through `crates/thinwire-ipc`: one JSON object per line on the helper's stdin and stdout. A change that an older peer cannot read must raise `PROTOCOL_VERSION`.
    - `HelperAdapter` (`thinwire-protocol`, module `helper`) is the only code that starts and stops a helper. It holds one process at most. `handle` only queues a message, so no caller waits on the pipe.
    - The helper starts when the user accepts the gate. It stops when the app closes. The app saves an accepted gate in `settings.toml` (`signal_notice_version`, `whatsapp_gate_version`). At the next start it sends the gate again, and the helper opens a saved, paired session with no QR code. Cancel clears the saved gate. If it ends, the adapter starts it again (1 s, 2 s, 4 s, 8 s) and sends the gate and the pairing again. After 5 failures the account row shows "Helper stopped." and Restart. Restart links a linked account again. A pairing that did not link ends at that stop: the user starts it again. A pairing also ends when the helper reports `Unlinked` or `AccountEnded`: no restart sends it again.
    - One helper process holds the lock file of the session folder. A second process refuses to run.
    - Each protocol has its own helper program and its own `HelperAdapter`. A stop of one helper does not stop the other. In the core, each protocol has its own pairing generation.
    - The phone number for a pair code crosses the pipe one time, in the `BeginLink` of the user. A restart sends the pairing again with no phone. `Debug` of a wire value shows no user data. Neither side logs message text, phone numbers, QR data, or pair codes.
    - Only the wire protocol goes to the helper's stdout. Logs go to stderr.
    - Media (wire version 4). A photo crosses as image bytes of 512 KiB at most (`WirePhoto`). `thinwire_protocol::photo_resize` (feature `photo-resize`) makes a larger photo a smaller JPEG. The Signal helper downloads the photos of a chat only while that chat is open. The WhatsApp helper downloads the photos of live rows and of the open chat, not of a history sync. The Discord adapter downloads the first image of each row when the chat opens. Audio crosses as a handle (`WireAudio`), and the helper downloads it only for `DownloadVoice`. The helper writes the file in `voice/` of its session folder (`thinwire_protocol::voice_files`: folder 0700, file 0600) and sends the absolute path in `VoiceReady`. The app opens only an absolute path. The helper empties `voice/` at start and when the device is revoked. The Discord adapter does the same in the user cache folder (`thinwire/discord/voice/`) and reads only HTTPS addresses on the Discord CDN hosts. A chat picture crosses as `WireEvent::Avatar` (wire version 5): a small JPEG from `photo_resize::avatar_from_bytes`. It sets only the picture of its row. The WhatsApp helper fetches the pictures of the 50 newest chats one time for each link, two at a time, and asks `groups().list_participating()` for the group names at each connection. A group that still has no name is asked for its subject (`groups().fetch_metadata`). The Signal helper sends a stored contact picture, and fetches a profile picture for a contact that has a profile key and no stored picture. It sends a cached group picture, and downloads one when the group has a picture path and the cache is empty. Each list is the first 50. Presage keeps a fetched picture in its store. A Signal person shows the contact name. If the contact has no name, it shows the Signal profile name, then the phone number, then "Signal user" and the first four characters of the id. The raw id does not show. The helper reads a stored profile name with the profile key of the contact, or with the key that Presage kept from a message. For the first 50 chats, it asks Signal one time for each link for a profile that is not in the store, and then it publishes the chat list again. A group sender uses the same name.
    - Mentions (wire version 7). A WhatsApp message keeps the mentioned JIDs of its context info, also in `inbox.sqlite`. The helper changes each "@" and user part to "@" and the name of that person: the chat name, then a push name. For a LID, the helper asks the device store one time for each connection for the phone JID (`get_lid_pn_entry`), and sends the rows of the open chat again. A mention crosses as `WireMessage::mentions`: a byte range and, when the helper has a one-to-one chat with that person, its conversation id. In the app, a mention is a `MessageLink` with `LinkTarget::Chat`. A click opens that chat. A mention with no chat has the link color and no click. The app drops a range that is not on the body, does not start with "@", overlaps, or names a chat of another protocol.
    - A helper starts with descriptors 0, 1 and 2 only. TDLib opens its sockets without close-on-exec, so the child marks every other descriptor close-on-exec between fork and exec (`helper::fds`, the one module with `unsafe` code). `scripts/fuzz-helper-fds.sh` is a stress run of it.
    - A helper writes only the log lines of thinwire targets (`helper::helper_log_target`). The protocol libraries log pairing data at level `info`, and the app logs each stderr line of a helper again. No `RUST_LOG` value turns a library target on.
- Discord: bot/OAuth guild inbox only — no self-bots / personal DMs / user tokens. Feature `discord-bot` (twilight HTTP) lists guild channels the bot can read, loads history, and sends as the bot. It runs in parallel with Telegram and does not wait for Telegram messages (lock change 2026-09-23; the code gate that waited is removed, `adfbb8c`, PR #40). Tests use a fake `DiscordApi`. ADR `0009-discord-bot-inbox-spike`. Default CI stays feature-off.
- Slack: official OAuth only — workspace app, not a personal desktop clone
- Signal: unofficial linked secondary device on `presage` — no supported third-party API, expect breakage. Experimental client is feature `signal-local` (`presage`, git rev pinned). Not the default UI. Default CI stays feature-off. Full-screen notice before any provisioning QR code. Session store stays in app-data (`thinwire/signal/`). The helper encrypts the live `session.sqlite`, the pending link file, and every retained `session.sqlite`. One OS keychain key (`signal.store_key`) opens all of them. The key does not cross the pipe. This encryption does not stop a program that runs as the same user and can read the keychain. A keychain that cannot save the key does not link, and it does not write a store. A keychain read that fails on a saved account keeps the row linked and does not move the store. Retry reads the key again. A first link shows "Signal did not link." A missing or wrong key keeps the store files: the helper moves them into a folder beside the session folder, leaves `helper.lock` in place, and the row leaves the linked state. It shows "Can't open the saved Signal session. Your old data is kept. Link again" and Link. Link starts the same QR flow as a removed device and does not delete the old files. If the helper cannot move those files, they stay in the session folder. Nothing is deleted. The row stays linked. It shows "The saved Signal session could not be moved aside. It was left in place. Nothing was deleted." and Retry. Retry tries the move again. It does not start a new link and it does not delete anything. A corrupt or unreadable file under `retained/` stays in place. The live session is not moved. The log line has no account id and no path. The client is `crates/thinwire-signal` (AGPL-3.0-only). It links Presage and libsignal, so it runs in the helper program `thinwire-signal-helper` (`0013`, #248; supersedes S2 / `0004` and `0011`), not in the app. `thinwire-protocol` keeps an MIT stub and the MIT helper adapter. It does not depend on the AGPL crate. The build of the client needs `protoc`: the nix shell has it, and other CI jobs run `scripts/install-protoc.sh`.
- Secrets: `keyring` OS store for Telegram `api_id` / `api_hash` / session and the Discord bot token (`discord.bot_token`). Phone / code / 2FA stay in the memory vault only. UI thread is memory-only; OS I/O is `spawn_blocking`. `THINWIRE_KEYRING=memory` for CI/headless. Never log secrets. Never put secrets on `AdapterCommand`. Never commit a Discord token. Feature `keychain-security-cli` (`thinwire-core`, macOS only) reads secrets through `/usr/bin/security` instead of the Keychain API, so a local rebuild does not ask for permission again. It is local only: `scripts/local-build.sh` is the one place that turns it on, `crates/thinwire-core/build.rs` stops a build under `CI` or `GITHUB_ACTIONS`, and `scripts/check-local-only-features.sh` (run by `scripts/test.sh`) keeps it out of the workflows, out of `default`, and out of every other feature list. Never add it to a workflow or a release build, and never call cargo with `--all-features` in CI. Feature `all-protocols` (`thinwire`) is the release feature list for a local build.
- Telegram live client is feature `telegram-tdlib` (`tdlib-rs`). Default CI stays feature-off. Unauthorized banner drops only on TDLib Ready. ADR `0006-live-tdlib`.
- Official `api_id` / `api_hash`: compile-time `TELEGRAM_API_ID` / `TELEGRAM_API_HASH` inject, never in git or public fork-PR CI. Official main OS zips (`.github/workflows/os-zips.yml`) read those names from GitHub repository secrets; local builds export them before cargo; public `ci.yml` never sets them. Values live in GitHub secrets and in arcoiro under the thinwire path (SOPS + Terraform, not watchkeep), not in this tree. Optional Advanced keychain override wins and is not the primary login path. Dev without inject shows credentials missing (not my.telegram.org). ADR `0007-publisher-telegram-api-credentials`. End-user official UX is phone → code → optional 2FA.
- Slack workspace-app spike is feature `slack-oauth` (`slack-morphism` OAuth v2 / Socket Mode; `hyper` on from 2026-09-24, `axum` off). Default CI stays feature-off. No Slack auth UI in the default shell. Client id, client secret, app-level token, and workspace bot token use the publisher inject / OS keychain pattern. ADR `0008-slack-oauth-workspace-spike`.

Job `nightly` puts the archives and the helper source on the `nightly` pre-release, with the version `<workspace>.r<commit count>.g<short sha>` in each name. Each archive stays 3 days |
| `.github/workflows/aur-nightly.yml` | Once a day, updates `pkgver` and the checksums of the AUR package `thinwire-nightly-bin` to the newest nightly. Secret `AUR_SSH_PRIVATE_KEY` is step env of that step only. The first version of the package is a manual push after a review |
| `.github/workflows/release-tag.yml` | Manual tag. No distroless GUI image |

## Commands

```bash
cargo build --workspace
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo run -p thinwire
cargo run -p thinwire-core --example headless
nix develop --command scripts/lint.sh
nix develop --command scripts/test.sh
nix develop --command scripts/test-release-features.sh
```

There is no server container. Do not add a distroless GUI Docker image.
