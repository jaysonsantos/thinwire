# Artifacts A: main-only OS zip artifacts

**Status:** accepted

## Context
Product-council (2026-09-20) locked CI packaging after option B. Developers need Windows, macOS, and Linux binaries from GitHub Actions. Those binaries must not look like a signed release. Pull requests must not upload OS zips. The project stays a desktop egui app. There is no distroless GUI Docker image.

Packaging correction (2026-09-23): `actions/upload-artifact` wraps every download in an outer zip and stores loose files as mode 644. Uploading `dist/` drops the executable bit, so `Thinwire.app` does not launch and the Linux binary is not runnable. The job uploads one `.tar.gz`. The outer zip is GitHub's wrapper. The tar.gz keeps Unix modes and the app bundle.

## Decision
CI uploads OS artifacts on **push to `main` only**. The Linux and Windows binaries are unsigned. The macOS app on `main` is Developer ID signed, notarized, and stapled (2026-11-05 amendment). An empty signing secret keeps the ad-hoc signature.

A matrix builds release binaries on Ubuntu, macOS, and Windows. Artifact names are `thinwire-linux-x86_64`, `thinwire-macos-arm64`, and `thinwire-windows-x86_64`. Retention is 7 days (short retention; delete-on-new-main is not needed). The workflow does not listen to `pull_request`. The upload job also requires `github.event_name == 'push'` and `github.ref == 'refs/heads/main'`.

GitHub always wraps the Actions download in an outer zip. That wrapper is unavoidable. The uploaded file is one `.tar.gz` built with `tar` after staging. The tar.gz preserves executable bits. Extract it to get the payload. Directory upload alone is not a ready-to-run artifact.

Linux and Windows tar members are flat. The binary, `LICENSE`, and `THIRD_PARTY_NOTICES` sit at the archive root. Linux also ships the TDLib LLVM C++ runtime libraries and their copyright files. The Linux and macOS binaries are mode `755` inside the tar.gz.

The macOS tar.gz contains a notarized and stapled `Thinwire.app`. `Contents/MacOS/thinwire` is the release binary and is executable in the archive. `Contents/Info.plist` sets `CFBundleExecutable` to `thinwire`, `CFBundleIdentifier` to `dev.jaysonsantos.thinwire`, `CFBundleName` and `CFBundleDisplayName` to `Thinwire`, and `CFBundlePackageType` to `APPL`. `CFBundleShortVersionString` and `CFBundleVersion` are the workspace package version. `LICENSE` and `THIRD_PARTY_NOTICES` sit in `Contents/Resources`. Extract the tar.gz and open `Thinwire.app`. Gatekeeper accepts that quarantined app. An empty `MACOS_SIGNING_P12` keeps the ad-hoc bundle from the 2026-09-29 amendment, and that build still needs Open Anyway.

Amendment (2026-09-29, #161): the stage script gives the whole bundle an ad-hoc signature (`codesign --force --sign -`) and checks it (`codesign --verify --strict`). Reason: thinwire-notify uses `UNUserNotificationCenter`, and that API needs a signed bundle whose signature binds `Info.plist` and the bundle id. Before this step, only the linker signed the binary. An ad-hoc signature has no identity. Gatekeeper still treats the app as software from an unknown developer. A downloaded archive usually has the `com.apple.quarantine` attribute, and the extracted app keeps it, so macOS blocks the first launch. The documented path is Gatekeeper's per-app override: after the blocked launch, System Settings > Privacy & Security > Security > Open Anyway (shown for about an hour), confirmed with Open and the login password. macOS saves `Thinwire.app` as an exception to the security settings. The command-line alternative removes the attribute: `xattr -dr com.apple.quarantine Thinwire.app`. Gatekeeper then does not check that copy at its first launch. This decision stays: no Developer ID and no notarization (Developer ID since 2026-10-29, see below).

Amendment (2026-10-24, stable signing identity): on push to `main`, the stage script signs `Thinwire.app` with the identity in the `MACOS_SIGNING_P12` secret. The log line `codesign identity:` shows the SHA-1 hash, the name, and the type (`Developer ID Application`, `self-signed`, or `unknown`). The job imports the identity into a temporary keychain. The sign command is `codesign --force --timestamp=none --sign "<identity>"`. The script adds `--options runtime` only when the type is `Developer ID Application`. A self-signed identity has no Team ID. Hardened runtime blocks `dlopen` of a bundled `libtdjson`. The script logs `codesign hardened runtime: on (Developer ID Application)` or `codesign hardened runtime: off` with the type. CI runs `codesign --verify --strict --deep --verbose=2`. If the secrets are not present (forks, pull requests), the script falls back to the ad-hoc signature of the 2026-09-29 amendment. Pull-request jobs do not read the secrets.

Reason: an ad-hoc signature has no stable identity, so macOS may ask for Keychain access again after each rebuild (inference, not verified on a Mac). A stable identity with the fixed `CFBundleIdentifier` `dev.jaysonsantos.thinwire` lets Keychain trust later builds. The first signed build asks one more time.

Amendment (2026-10-25, signing identity recorded): CI signs with an Apple Development identity. The Team ID is 89SP4VB8Y7. This identity is not a Developer ID Application identity. This identity is not self-signed. The script logs the type as `Apple Development`. The script does not add `--options runtime` when the type is `Apple Development`. The certificate chain is Apple Development, then Apple WWDR CA G3, then Apple Root CA. Hardened runtime is off. Public distribution still needs a Developer ID Application identity and notarization.

Consequences: Keychain authorization follows the designated requirement ([Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)). The default Apple Development requirement checks the bundle id, the Apple certificate chain, and the leaf subject CN. It does not check the certificate fingerprint. A renewal of the same identity can keep the same designated requirement. That renewal can keep the existing authorization. Another Keychain prompt occurs only when the renewal changes the designated requirement, for example another developer identity or a different subject CN. Keep a backup of the `.p12`. The script logs the type as `Apple Development`. The script signs without `--options runtime` when the type is `Apple Development`, `self-signed`, or `unknown`. Gatekeeper still blocks the first launch, and Open Anyway stays the documented path. There is no notarization. A Developer ID identity without notarization does not remove the Gatekeeper block.

Amendment (2026-10-29, Developer ID identity): the owner replaced `MACOS_SIGNING_P12` and `MACOS_SIGNING_P12_PASSWORD` with a Developer ID Application identity from the same team (Team ID 89SP4VB8Y7). Run 40616829366 (attempt 2) on `main` logs the type as `Developer ID Application` and signs with `--options runtime`. The CodeDirectory flags are `0x10000(runtime)`, so hardened runtime is on. The 2026-10-25 amendment is superseded for the identity type and the hardened runtime. The designated requirement changes with the identity type, so the first Developer ID build asks for Keychain access one more time. Click Always Allow. The Developer ID requirement checks the bundle id, the Team ID, and Apple's Developer ID CA marker. It does not check the certificate name. A renewal from the same team should keep the Keychain authorization (not tested). The 2026-10-25 text about the Apple Development requirement and the certificate name no longer applies. There is still no notarization, so Gatekeeper still blocks the first launch and Open Anyway stays the documented path. Notarization needs a separate council decision. The "Rejected" list below no longer rejects a Developer ID signature. It still rejects notarization.

Amendment (2026-11-05, notarized main artifact): the main macOS artifact is Developer ID signed with a secure timestamp (`codesign --timestamp`), notarized, and stapled, then packed with the same tar.gz. This supersedes `--timestamp=none` for a Developer ID Application identity, and it supersedes the "no notarization" sentences in the 2026-10-29 amendment. Notarization is no longer in the Rejected list. Artifacts are still not a release. Retention, the main-only trigger, and the empty-p12 ad-hoc path stay. A Developer ID signature that does not staple fails the job, so an unstapled Developer ID app is not uploaded. Notary auth is one App Store Connect API key. The macOS stage step is the only step that receives `MACOS_NOTARY_KEY`, `MACOS_NOTARY_KEY_ID`, and `MACOS_NOTARY_ISSUER`. `notify-os` does not receive them. An empty `MACOS_SIGNING_P12` still signs ad-hoc. Staple skips that signature when the notary variables are unset, which is the `notify-os` path. On the main stage step those variables are set, so an empty p12 fails the job instead of uploading an ad-hoc app. Gatekeeper accepts a quarantined `Thinwire.app` from this artifact. Open Anyway, and `xattr -dr com.apple.quarantine`, stay the path for an ad-hoc build.

Existing lint, test, build, and `check` jobs stay as they are. README states that the artifacts are not a release. The main macOS artifact is notarized and stapled.

## Consequences
A `main` push keeps three short-lived artifacts. Each download is an outer zip around one tar.gz. Reviewers do not get OS artifacts from pull-request CI. Users must not treat them as a release. The macOS artifact is notarized and stapled, and it is still not a release. A later release path needs a new council lock.

Rejected: PR artifact uploads; distroless GUI image; delete-on-new-main (short retention is enough); uploading the raw directory (it drops execute bits); a zip whose only member is an identical zip.
